# idle-ti.me website

![GitHub last commit (by committer)](https://img.shields.io/github/last-commit/be-next/idle-ti.me?logo=github)
![GitHub Actions Workflow Status](https://img.shields.io/github/actions/workflow/status/be-next/idle-ti.me/publish.yml?label=build%20%26%20publish)

Source of [idle-ti.me](https://idle-ti.me) — articles, curated tools and projects on performance engineering and observability. The site is built with [Zola](https://www.getzola.org) and the [tabi](https://welpo.github.io/tabi) theme, and served from Amazon S3 through CloudFront.

## Stack

| | |
|---|---|
| Generator | Zola 0.23.6, pinned in CI |
| Theme | tabi v5, as a git submodule in `themes/tabi`, kept up to date by Dependabot |
| Hosting | private Amazon S3 bucket behind CloudFront, DNS in Route 53 |
| CI/CD | GitHub Actions: build and Lighthouse budget on every pull request; measure, deploy and check the budget on every push to `main` |
| Comments, analytics | giscus, Umami |

## Local development

```bash
git clone --recurse-submodules https://github.com/be-next/idle-ti.me.git
cd idle-ti.me
zola serve --drafts   # http://127.0.0.1:1111
zola build            # production build into ./public
```

Use Zola 0.23.6 locally as well: tabi v5 relies on Tera 2 components, which older versions of Zola cannot parse. If the repository was cloned without its submodules, run `git submodule update --init --recursive`.

## Writing content with Zola 0.23

Zola 0.23 moved to Tera 2, which changes two things when writing Markdown:

- **Shortcodes are now components.** Block form: `{% <references> %} … {% </references> %}`. Inline form: `{{< number_card value="8" label="industries" />}}` — arguments are separated by spaces, not commas.
- **`{{ … }}` and `{% … %}` are parsed inside fenced code blocks too.** Wrap any sample that contains them — a GitHub Actions `${{ secrets.X }}`, Jinja, JSX — in `{% raw %}` / `{% endraw %}`.

The tools page, `content/awesome-performance-engineering/_index.md`, is generated: change the source repository or the sync script, never the file itself.

After adding a post or changing a title or description, redraw the social media cards; after changing the site title or menu, regenerate the fonts. Both scripts need `pip install fonttools brotli pillow`:

```bash
python3 scripts/social_cards.py    # one card per page, plus the site-wide one
zola build && python3 scripts/subset_fonts.py   # also lists characters the subsets miss
```

## Front end

- **Fonts.** tabi ships Inter and Source Serif with every script they cover. `scripts/subset_fonts.py` keeps Latin, Latin Extended-A and the punctuation the posts use, and writes the result to `static/fonts/` under the theme's file names, which Zola serves in place of the theme's: 198 KB of fonts per page instead of 411 KB. It also cuts the header font (`static/custom_subset.css`) to the site title and menu.
- **Colours.** `skin = "accessible_orange"` is tabi's `lowcontrast_orange` with a darker light-theme orange, #c25400 (4.6:1 on white instead of 3.02:1). Links in running text are underlined, and the header icons are 24 px touch targets.
- **Navigation.** Speculation Rules prefetch a page when the reader hovers its link, and a cross-document view transition fades from one page to the next (off with `prefers-reduced-motion`).
- **Social cards.** Every page has an `og:image`: its own 1200×630 card, or the site-wide one.
- **Content Security Policy.** tabi emits it as a `<meta>` tag from `allowed_domains` in `config.toml`, and adds the Umami and giscus domains itself.
- **Budget.** Lighthouse CI measures five representative pages (`scripts/measure.sh`) and fails when a page drops below 95 in performance or 100 in accessibility, best practices or SEO, when LCP exceeds 2.5 s, CLS 0.05 or TBT 100 ms, or when fonts exceed 225 KB. `validate.yml` checks it on every pull request; `publish.yml` measures every deploy and checks the budget once the site is live, so a regression flags the commit without holding back the publication. The reports are kept as a workflow artifact for 14 days.
- **Performance page.** [/performance/](https://idle-ti.me/performance/) publishes each deploy's figures: `scripts/performance_data.py` turns the Lighthouse reports into `content/pages/performance/data.json` (not committed, published next to the page), which the `performance_report` component renders. A build without that file shows the page without figures.

## Deployment

On every push to `main`, `publish.yml`:

1. measures the site with Lighthouse CI and writes the figures of the performance page; a failed measurement doesn't stop the deploy;
2. builds the site with `zola build`;
3. authenticates to AWS through GitHub OIDC: no long-lived access key, just short-lived credentials for an IAM role that only this repository's `main` branch can assume;
4. syncs the static assets to S3 with `Cache-Control: public, max-age=31536000`;
5. syncs the content (HTML, XML, JSON, TXT) with `Cache-Control: public, max-age=0, s-maxage=31536000, must-revalidate`: browsers revalidate on every visit, while CloudFront keeps the pages at the edge;
6. invalidates `/*` on CloudFront, which is what purges that edge-cached content;
7. checks the Lighthouse budget: a page over budget, or a failed measurement, turns the run red after the deploy.

Both syncs use `--delete`, so a file that leaves the build leaves the bucket too. S3 versioning keeps every overwritten or deleted object for 5 days.

The CloudFront side is configured in AWS, not in this repository:

- CloudFront reads the private bucket through an Origin Access Control;
- a CloudFront Function on viewer requests appends `index.html` to directory URLs;
- a custom error response turns the 403 that S3 returns for a missing key into `/404.html` with a 404 status;
- a cache policy honours the origin `Cache-Control`, keys on Zola's `?h=` cache-busting hash, and serves Brotli;
- a response headers policy adds HSTS, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy` and `Permissions-Policy`;
- HTTP/3 and IPv6 are enabled, and Route 53 holds A and AAAA aliases plus a CAA record for ACM.

The article [Zola: How to deploy a website using S3 Bucket and CloudFront](https://idle-ti.me/blog/zola-aws/) explains each of these choices and gives the configurations to reproduce them.

Repository secrets used by the workflows: `AWS_ROLE_ARN` (the deploy role), `S3_BUCKET`, `CLOUDFRONT_DISTRIBUTION_ID`, and `PUSH_TOKEN` for the tools-page sync.

### Code highlighting

`config.toml` sets a light (`github-light`) and a dark (`catppuccin-frappe`) highlighting theme. Zola generates one stylesheet per theme and tabi loads both unconditionally, so the dark palette would win everywhere. `static/syntax-dual.css`, loaded last, scopes each palette to its own theme and follows tabi's theme switcher. Regenerate it after changing either theme: the procedure is in its header.
